Project Overview

Why Atlas exists

What problem existed?
Engineering knowledge lived in disconnected wikis, Slack threads, and people's heads. When someone left or a service changed hands, context evaporated. Search returned filenames, not meaning.
Why was this project created?
To give teams a single, live source of truth that is editable offline, merges without conflicts, and answers questions in natural language — not just keyword matches.
Who are the users?
Platform and product engineers at 40–400-person companies who maintain shared systems, runbooks, and architecture decisions that must stay current.
What value does it provide?
Faster onboarding, fewer repeated questions, and institutional memory that survives reorgs. Teams report cutting time-to-find documentation by roughly 40%.

Development Highlights

Engineering work that mattered

Not feature checkboxes — the hard parts, and how they were actually solved.

01

Authentication

SSO · Sessions
Problem

Enterprise teams required SAML/SCIM but still expected instant, passwordless sign-in on the web app.

Solution

Hybrid auth: OIDC for interactive login, short-lived JWTs with rotating refresh tokens, SAML brokered through a dedicated IdP proxy.

Implementation

Built a token store that survived reloads and tab switches, with silent refresh 60s before expiry to avoid UI flicker.

Result

Zero login-related support tickets after launch; passkey enrollment adopted by 62% of users in month one.

02

Offline Support

Local-first
Problem

Field and travel-heavy engineers lost edits whenever the train tunnel or café Wi-Fi dropped.

Solution

A local-first store (IndexedDB) holding a CRDT replica; writes apply optimistically and reconcile on reconnect.

Implementation

Serialized the document as a sequence of operations, persisted the op-log locally, and replayed it against the server's timeline with causal ordering.

Result

Edits never lost; merge conflicts resolved automatically in 99.4% of reconnects without user intervention.

03

Real-time Communication

CRDT · WebSocket
Problem

Multi-cursor editing and live presence had to feel instantaneous across continents, not just one office.

Solution

Rust WebSocket gateway broadcasting CRDT ops, with presence diffs batched at 30fps and interpolated on the client.

Implementation

Used a hybrid of authoritative server ordering and local echo; cursor positions sent over a separate lightweight channel to keep doc ops clean.

Result

p90 presence latency of 80ms globally; smooth co-editing sessions with up to 14 concurrent users.

04

AI Integration

Embeddings · LLM
Problem

Keyword search missed intent; teams asked questions, not queries, and expected sourced answers.

Solution

Chunked docs into embeddings stored in Postgres pgvector, retrieved top-k, then grounded an LLM answer with citations.

Implementation

Re-embedded only changed blocks via a CDC pipeline; cached retrieval results at the edge with a 10-minute TTL keyed by doc version.

Result

Semantic answers in ~700ms p50; every answer links back to the source block for trust and verification.

05

Caching & Performance

Edge · Virtualization
Problem

Feature growth pushed the initial bundle past 1.4MB and made large docs janky to scroll.

Solution

Route-level code-splitting, an edge cache for public workspace shells, and windowed virtualization for long documents.

Implementation

Adopted React Server Components for static shells, lazy-loaded the editor, and virtualized the block list with fixed-size measurement.

Result

Initial JS cut by 61% to 540KB; time-to-interactive dropped from 3.1s to 1.2s on mid-tier devices.

Challenges & Solutions

The decisions that defined the build

The interesting part of any real product is what broke and why the fix looks obvious in hindsight.

C1
Conflict-free editing when nobody is online together
Problem
Two engineers editing the same doc offline for a day produced divergent states that naive last-write-wins destroyed.
Approach
Evaluated OT vs CRDT; chose CRDT (RGA + map) for commutative merges without a central arbiter.
Final Solution
Per-block CRDT with operation logs persisted locally and replayed with causal ordering on reconnect.
Outcome
Automatic merge in 99.4% of cases; manual resolve only for true semantic conflicts.
C2
Presence that feels alive across the planet
Problem
Raw WebSocket broadcasts saturated bandwidth and jittered on high-latency links between regions.
Approach
Separated cursor/presence traffic from document ops; batched and interpolated rather than streaming raw.
Final Solution
Edge-terminated sockets with a regional fan-out mesh; client-side easing smoothed 30fps diffs.
Outcome
80ms p90 presence latency globally; bandwidth down 7×.
C3
Semantic search that was fast and cheap
Problem
Re-embedding whole docs on every keystroke was slow and expensive; stale answers eroded trust.
Approach
Block-level embeddings via a CDC pipeline, plus retrieval caching keyed by doc version.
Final Solution
Only changed blocks re-embed; edge cache served repeat queries; LLM grounded with citations.
Outcome
~700ms p50 answers; embedding cost per doc edit cut 90%.
C4
Shipping features without bloating the bundle
Problem
Editor, AI, and insights in one bundle pushed load time past 3s on mid-tier phones.
Approach
Treat the shell as static, lazy-load everything interactive, virtualize long content.
Final Solution
RSC static shells, route-split chunks, windowed block rendering, strict bundle budgets in CI.
Outcome
Initial JS −61%; TTI 3.1s → 1.2s.
C5
Zero-downtime schema changes on live data
Problem
CRDT schema evolved; migrations had to run without locking tables or dropping a single op.
Approach
Expand-contract pattern with dual-write and a backward-compatible op decoder.
Final Solution
Versioned op format; migrations ran online with shadow reads before cutover.
Outcome
0 downtime incidents across 11 schema migrations in production.

Developer Reflection

What I'd tell my past self

Atlas taught me that the hardest part of real-time software isn't the algorithms — it's making failure invisible. The CRDT math was the easy quarter; the hard part was the reconnect path, the stale-cache path, and the "two people typed the same word" path nobody plans for in a demo.

What I learned

Local-first is a product decision, not just an architecture one. Once edits never disappear, users stop saving defensively and start collaborating naturally.

What I'd improve

I'd invest in end-to-end type safety across the WebSocket boundary from day one. We lost more time to op-shape drift than to any algorithm bug.

Interesting decisions

Keeping AI retrieval on a separate channel from document ops was the call that kept search fast without ever risking a lost edit.

Future roadmap

Conflict-free mobile sync with CRDT compaction, and an agent mode that proposes doc updates from merged PRs automatically.
